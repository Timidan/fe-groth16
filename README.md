# fe-groth16

**Pitch:** fe-groth16 lets Fe contracts verify Groth16 proofs made with circom and snarkjs, and includes a key converter and an example bounty contract.

```fe
use ingot::preimage_key::PREIMAGE_VK

// Two public inputs, so the key is a VerifyingKey<2> and the inputs a [u256; 2].
// Any other length is a type error.
verify(vk: PREIMAGE_VK, proof, inputs: [hash, recipient.word()]).is_ok()
```

## The problem

circom and snarkjs are the most widely used toolchain for zero-knowledge circuits on Ethereum, but the only on-chain verifier snarkjs exports is Solidity. A Fe project that wants to accept a proof has two options: deploy a Solidity contract next to it, or write the verifier by hand. A hand-written verifier is easy to get subtly wrong. You have to negate `A`, swap the halves of every G2 coordinate into precompile order, and reject public inputs at or above the field order. If you skip that last check, `x` and `x + r` both verify, which breaks any nullifier built on an input.

## Approach

All of this was built during the contest:

- **`verify`** ([`src/lib.fe`](src/lib.fe)) checks a proof against a key with the BN254 precompiles (`ecAdd`, `ecMul`, `ecPairing`) from Fe's standard library. It accepts every canonically encoded proof that snarkjs's Solidity verifier accepts, and it is stricter about encoding: the Solidity verifier accepts five encodings of `A.y` for each proof, `verify` accepts one. [A differential test](#compared-with-snarkjss-solidity-verifier) checks both in CI. It returns a `Result<Rejection, ()>` that says why a proof failed, and it rejects malformed proofs before the precompiles, where a failed call would consume all the gas it was given.
- **`scripts/snarkjs2fe.mjs`** converts a snarkjs `verification_key.json` into a Fe module ([`src/preimage_key.fe`](src/preimage_key.fe)). The module holds the key as a compile-time constant and a verifier contract with the same selector and arguments as the Solidity verifier snarkjs exports, so callers don't change. It refuses numbers that are not decimal strings (a JSON number would already have been rounded) and G1 points off the curve.
- **`PreimageBounty`** ([`src/bounty.fe`](src/bounty.fe)) pays its balance to whoever proves they know a preimage of a Poseidon hash, without revealing it. The recipient is a public input of the proof, so anyone who copies a pending claim from the mempool can only pay the original claimant.
- **Two circuits** ([`circuits/`](circuits)) and proofs generated by snarkjs 0.7.6 serve as test vectors: a one-constraint multiplier with one public input, and the 416-constraint Poseidon preimage circuit with two.

## Fe highlight

The circuit's input count is a const generic shared by the key and the inputs:

```fe
pub struct VerifyingKey<const N: usize> {
    pub alpha: G1,
    pub beta: G2,
    pub gamma: G2,
    pub delta: G2,
    pub ic0: G1,
    pub ic: [G1; N],
}

pub fn verify<const N: usize>(vk: VerifyingKey<N>, proof: Proof, inputs: [u256; N]) -> Result<Rejection, ()>
```

So passing three inputs to a two-input key doesn't compile:

```text
error[8-0000]: type mismatch
  ┌─ src/example.fe:6:49
  │
6 │     verify(vk: PREIMAGE_VK, proof: BOB, inputs: [1, 2, 3]).is_ok()
  │                                                 ^^^^^^^^^ expected `[u256; 2]`, but `[{integer}; 3]` is given
```

Fe's `Result` is `#[must_use]`, so calling `verify` and forgetting to check the answer, the classic verifier misuse, is a compile error (`unused value of type Result<Rejection, ()>`); dropping it takes an explicit `let _ =`.

`verify` has no `uses` clause, so it is handed no capability at all: the compiler rejects any storage access, event, value transfer or contract call in it. Its only external calls are the BN254 precompiles, reached through std's `crypto` wrappers, which use an intrinsic internal to std and restricted to precompile addresses. That restriction is a property of std, not something the compiler checks in user code. Fe carries the absence of effects into the ABI: the generated `verifyProof` is `pure`, where snarkjs's Solidity verifier is `view`. In `PreimageBounty`, the only handler that can move funds is the one that declares `mut call`:

```fe
Claim { a, b, c, recipient } -> Wei uses (ctx, mut call, hash, mut claimed, mut log) {
    assert!(!claimed, "Already claimed")
    let proof = Proof::from_calldata(a, b, c)
    assert!(verify(vk: PREIMAGE_VK, proof, inputs: [hash, recipient.word()]).is_ok(), "Invalid proof")
    ...
}
```

## Demo

`scripts/demo.sh` runs the bounty end to end on a local anvil chain, with a fresh secret and a fresh proof each time. Alice is paid through a contract wallet that records each payment in storage, which a bare 2,300-gas transfer could not pay. ([Full transcript](docs/demo.md).)

```text

== The same proof cannot be used again

```

## Compared with snarkjs's Solidity verifier

`scripts/compare.mjs` deploys the Fe verifier and the Solidity verifier snarkjs exports for the same key to anvil, then checks three things in CI on every push:

- **15 fixed cases per circuit:** valid proofs, a wrong input, an input `x + r`, a proof from another circuit, tampered or swapped points, out-of-range coordinates, points off the curve or twist, the all-zero proof, and a non-canonical `A.y`. Both return the same result in 28 of the 30 cases. The two differences are the non-canonical `A.y`, where Solidity accepts and Fe rejects. snarkjs negates `A` as `(q - y) mod q` in 256-bit arithmetic, so `y + (2^256 mod q)` and three more values above `q` wrap to the same point, and the same proof is accepted under five different calldata encodings.
- **16 fresh proofs** generated by snarkjs for random and edge-case inputs (public values `0`, `1` and `r - 1` among them). Both verifiers accept every one.
- **500 seeded single-word mutations** of a valid proof and its inputs (random words, bit flips, `+ q`, `+ r`, `- 1`, zero). Both verifiers reject every one.

Gas per transaction (`gasUsed` with a 1,000,000 limit; [full table](docs/compare.md)):

| Preimage circuit, 2 inputs | Solidity (solc 0.8.28, optimized) | Fe 26.6.0 |
| --- | --- | --- |
| Valid proof | 221,411 | 225,021 (+1.6%) |
| Wrong input, tampered `A`, `B` or `C` | 221,399 – 221,423 | 225,042 – 225,066 |
| `A` or `C` off the curve, coordinate ≥ `q` | 985,049 – 985,060 (nearly the whole limit) | 31,170 – 33,000 |
| `B` off the twist | 985,060 | 985,181 |
| `A.y` written as `y + (2^256 mod q)` | accepted, 221,411 | rejected, 33,000 |
| Runtime bytecode | 1,439 bytes | 3,284 bytes |

A valid proof costs about 3,600 gas more in Fe, so a caller that forwards just enough gas for the Solidity verifier would see Fe's run out. For a malformed `A`, `C` or coordinate, the costs differ in kind: the Solidity verifier hands the point to the pairing precompile, and the failed call burns nearly all the gas the caller supplied, so its cost grows with the gas limit. `verify` refuses the point first, for a fixed 31,000–33,000 gas.

## Architecture

| Path | Contents |
| --- | --- |
| `src/lib.fe` | `G1`, `G2`, `Proof`, `VerifyingKey<N>`, `Rejection`, `verify` |
| `src/multiplier_key.fe`, `src/preimage_key.fe` | Generated: each circuit's key and its `verifyProof` contract |
| `src/bounty.fe` | `PreimageBounty`, the example application |
| `src/vectors.fe` | Generated: the snarkjs proofs and public inputs the tests use |
| `src/tests.fe`, `src/bounty_tests.fe` | Tests |
| `scripts/snarkjs2fe.mjs` | snarkjs JSON to Fe converter (Node, no dependencies) |
| `scripts/setup.sh`, `scripts/prove.sh`, `scripts/gen.sh` | Build the circuits and keys, make a proof, regenerate the Fe sources |
| `circuits/`, `vectors/` | circom sources, proving and verifying keys, proofs |

```
circuit.circom ─circom─▶ r1cs ─snarkjs setup─▶ verification_key.json ─snarkjs2fe─▶ <name>_key.fe ─fe build─▶ verifier contract
                                     └─▶ circuit.zkey ─snarkjs prove─▶ proof.json, public.json ─▶ verifyProof / claim calldata
```

## Build and test

```sh
fe --version   # fe 26.6.0
fe test
fe build       # writes out/*.bin and out/*.abi.json
```

`fe test` needs only Fe. Everything else needs Node 18 or later and `npm ci`. The demo and the comparison also need anvil and cast from [Foundry](https://getfoundry.sh), and the demo needs `jq`:

```sh
scripts/demo.sh                                  # the bounty, end to end on anvil (PORT=8548 by default)
node scripts/compare.mjs                         # Fe vs Solidity verifier; writes docs/compare.md (run fe build first; PORT=8547)
scripts/gen.sh                                   # vectors/*.json -> src/*_key.fe, src/vectors.fe
scripts/prove.sh preimage input.json out_dir     # a new proof against the committed key
scripts/setup.sh                                 # new circuits and keys (changes every key)
```

To verify your own circuit, export its `verification_key.json` with snarkjs (as `scripts/setup.sh` does), run `node scripts/snarkjs2fe.mjs key <name> verification_key.json > src/<name>_key.fe`, then call `verify(vk: <NAME>_VK, ...)` or deploy `<Name>Verifier`.

CI runs `fe fmt --check`, `fe test` and `fe build`, regenerates the Fe sources from the committed snarkjs files and fails if they differ, runs the comparison against the Solidity verifier, and runs the demo from a clean checkout.

## Tests

| Claim | Test |
| --- | --- |
| Proofs generated by snarkjs verify, for 1 and 2 public inputs | `snarkjs_proofs_verify` |
| A second proof of the same statement verifies too, so proof bytes are no nullifier | `second_proof_of_same_statement_verifies` |

| A `B` off the twist is refused by the pairing precompile | `invalid_g2_point_is_rejected` |
| The all-infinity proof is refused | `proof_at_infinity_is_rejected` |
| The generated contracts answer `verifyProof` calls like snarkjs's Solidity verifier | `generated_verifier_contracts` |
| The bounty pays the proven recipient, once, and a copied proof can't redirect it | `valid_claim_pays_the_recipient`, `copied_proof_cannot_redirect_payout`, `bounty_pays_once` |

| The bounty pays a contract wallet that writes storage, with a fresh proof, end to end | `scripts/demo.sh` (CI) |

## Limitations

- The keys come from a local setup with a single contributor, so whoever ran it could forge proofs. That's fine for tests and demos, not for real value. For production, use a key from a multi-party ceremony and convert it with `snarkjs2fe.mjs`.
- When the pairing precompile rejects `B`, the failed call consumes all the gas it was given, as it does in snarkjs's Solidity verifier. `verify` checks `A`, `C` and every coordinate's range itself, but checking that `B` is on the twist and in its subgroup in Fe would cost more than the precompile. A contract that pays for other people's proofs should bound the gas it forwards to verification.
- The precompile wrappers report a failure without its cause. `PairingCallFailed` therefore means an invalid `B`, an invalid key point, or too little gas, and `CommitmentCallFailed` means an invalid key point or too little gas. Key points are checked once, by the converter, not on every call.
- A valid proof costs about 1.6% more gas than with snarkjs's Solidity verifier, and the Fe contract's runtime code is about 2.3 times larger (3.3 KB against 1.4 KB), well under the 24 KB limit.
- The converter checks G1 key points against the curve but G2 points only against the field range. A bad G2 point makes every proof fail; it cannot make a forged proof pass. Circuits need at least one public input.
- Only Groth16 on BN254 is supported. There is no PLONK, fflonk, BLS12-381 or batch verification.
- The circuits are examples. The bounty pays a single claim in ETH and has no refund path.
- Fe is not production-ready, and none of this has been audited.
